# 初版使用边界

版本：2026.09.11-r1。维护责任角色：设计系统负责人（待认领）。更新：2026-09-11。

本版可用于查资料、定位 Figma、设计评审准备、生成待评审方案和培训。不能据此宣称全量规范已人工确认、线上实现已对齐或自动生成页面可免审上线。

## 两个独立维度

确认状态沿用项目定义：草稿、待确认、已确认、有争议、已废弃。证据类型描述结论从哪里来，不能代替确认状态。

| 证据类型 | 可陈述 | 不可陈述 |
| --- | --- | --- |
| figma-traceable | 该节点或备注记录了某事实 | 已获负责人批准、线上一定生效 |
| observed-web | 某次公开文本中出现了某内容 | 全端永久规则、未观察到的交互与尺寸 |
| project-policy | 本项目约定如何管理知识 | 公司全部设计规则已通过审核 |
| proposal | 本版建议如何处理 | 现行规范要求如此 |
| inferred / unknown | 有线索或证据不足 | 凭外观补齐业务用途 |

当前新增档案全部为待确认。文中的“建议”仅支持可逆原型和评审准备；需上线、建立正式 Token 或改变分流逻辑时，应由对应负责人确认。

## 来源与冲突

来源注册在 [sources.json](sources.json)。每个知识档案保留来源 ID、责任角色、日期和待确认项。未获得真实姓名时写“待认领”，不把 AI 写成审批人。

同一事实只维护一个权威档案；索引、网页和汇报数据由构建脚本派生。卡片原始事实仍以扫描快照为准，精炼档案记录解释边界和评审建议。编号与页面关系不在精炼档案中重复列全量副本。

设计要求与线上实现分开记录。具体版本例外须有证据；未确认的版本备注不自动转换为当前 A/B 配置，也不意味着旧状态已废弃。

## 试用时的回答格式

先给结论及适用范围，再给知识版本、证据类型、节点或档案链接，最后说明未确认项和可采取的下一步。搜索命中不是业务适用证明；空结果应明确回答“当前库没有足够证据”。

## 发布条件

运行 `npm run build`、`npm run validate`、`npm test`。生成的网页与索引须与源文档一致。修改来源或规则时更新 CHANGELOG 和版本；本地发布不等于外网部署。人工确认必须包含真实确认人、日期和结论，并关闭关联问题。
