# 协作与确认流程

## 角色分工

| 角色 | 负责内容 |
| --- | --- |
| 设计系统负责人 | 维护模板、分类、设计原则和最终发布标准 |
| 业务设计师 | 按业务家族认领，补用途、场景、状态和页面关系 |
| 研发代表 | 确认组件、接口字段、端型差异和线上实现 |
| 测试代表 | 补边界条件、验收标准和回归范围 |
| 产品 | 确认会改变业务含义、用户行为或分流逻辑的争议 |
| 管理员 | 汇总修改、检查冲突、更新版本和发布 |

## 推荐协作方式

1. 管理员按卡片家族或页面模块建立认领清单。
2. 每位设计师只编辑自己认领的 `knowledge/` 文档，并保留来源链接。
3. 设计师完成后将状态改为“待确认”，写明需要谁确认。
4. 设计或研发确认后记录姓名、日期和结论；争议项保持“待确认”。
5. 管理员统一合并，运行检查，更新变更记录后发布网站和 Skill。

## 状态定义

| 状态 | 含义 |
| --- | --- |
| 草稿 | 正在整理，不能作为正式结论 |
| 待确认 | 字段已补充，等待负责人复核 |
| 已确认 | 负责人已经确认并留有记录 |
| 有争议 | 设计、研发或产品结论不一致 |
| 已废弃 | 有明确废弃结论，历史档案继续保留 |

第一阶段继续使用一位管理员统一发布。等多人同时编辑、权限、审批和实时同步成为真实负担，再引入数据库或正式后台。
