# 卡片库重新入库识别规则

## 为什么需要重做

旧版主要依赖组件/Frame 的节点名称和较大的展示区域，因此会出现两类错误：

1. 只识别到名为 `39001-ios` 的视觉节点，漏掉标题中真正的卡片编号 `3900101`。
2. 把左侧说明文字和右侧卡片本体所在的整行 `card` Frame 当作预览边界，导致备注被截入卡片图片。

2026-09-01 的重新审计在 11 个有效 Figma 页面中找到 349 个编号标题出现位置、260 个唯一权威编号；旧版只有 97 个编号，至少漏掉 169 个。

## 四层结构

每个卡片区域按以下四层保存，不再混成一个节点：

1. **编号标题**：标题组件中字号形式的编号，是卡片 ID 的权威来源。
2. **标题说明**：编号右侧的名称/说明，例如“好价榜/品类榜卡片基于 39001 微调”。它用于命名、用途理解和父卡关系提取。
3. **行内备注**：卡片左侧的状态、差异或变更说明，例如“增加角标”。它进入备注、状态或变更字段，不进入预览。
4. **卡片本体**：同行右侧真正承载卡片视觉的 Frame、Component、Component Set 或 Instance。只有它可以作为卡片预览和样式提取范围。

## 权威优先级

1. 卡片编号以“卡片编号”标题组件里的字号为准，即使视觉节点仍沿用旧名称。
2. 卡片正式名称优先取编号右侧标题说明。
3. 视觉节点名称仅作为别名和追溯信息，不能覆盖标题编号。
4. 同一编号在 iOS/Android 多处出现时合并为一个卡片档案，分别保存平台样例。
5. 一个编号下面出现多行卡片本体时，先作为同一卡片的状态/差异样例归档；含义不明时进入待确认，不另造编号。
6. 明确废弃或置灰的记录保留，但生命周期标记为废弃；不能因为无人确认而删除。

## 卡片本体边界识别

在编号标题之后、下一个编号标题之前：

- 找到名称为 `card` 的展示行；
- 将行内左侧的 TEXT 节点识别为备注；
- 将右侧尺寸和内容符合卡片的 FRAME、COMPONENT、COMPONENT_SET 或 INSTANCE 识别为卡片本体；
- 如果一个展示行存在多个候选本体，保留候选并交由设计确认；
- 预览只导出本体节点，不导出 `card` 展示行、标题、备注或分隔线。

不能仅凭“节点名称包含编号”判断卡片本体。Frame 可能沿用基础卡名称，标题编号仍然是正确的新编号。

## 3900101 验证样板

- 权威编号：`3900101`
- 标题说明：好价榜/品类榜卡片基于 39001 微调
- 父卡线索：`39001`
- 编号标题节点：`2400:12063`
- 展示行一：`2400:12064`
  - 备注：`1、增加角标`
  - 卡片本体：`2400:12066`，Frame 名仍为 `39001-ios`
- 展示行二：`2400:12085`
  - 备注：`2、增加“同款上榜商品”模块`
  - 卡片本体：`2400:12087`，Frame 名仍为 `39001-ios`

因此 `3900101` 必须作为独立卡片编号入库；两个 `39001-ios` Frame 是其视觉样例，左侧两段说明是变更/状态备注，不属于卡片截图。

## 新档案需要增加的字段

- `authoritativeIdSource`：权威编号文本节点。
- `titleDescription`：编号右侧说明。
- `baseCardId`：从“基于 39001 微调”等文案提取的父卡线索。
- `annotationNodes`：备注文本节点及原文。
- `visualNodes`：卡片本体节点、类型、尺寸和平台。
- `visualNodeNameMismatch`：本体名称与标题编号不一致时记录。
- `examples`：一个编号下的多种状态或差异样例。
- `lifecycleEvidence`：废弃、置灰、实验等状态的来源。

## 发布限制

重新扫描完成前，旧版“97 张卡片”只能视为第一批样本，不能再表述为完整卡片库。新版本发布前必须校验：

- 所有标题编号均已进入档案或异常清单；
- 所有预览均不包含备注区；
- 长编号不会被五位编号正则截断或忽略；
- 视觉节点名称与标题编号不一致时不会错误合并；
- 备注原文可追溯，但与卡片本体视觉分离。
