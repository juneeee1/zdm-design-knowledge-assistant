# 值得买「设计规范 AI 知识库」建设路线图

## 一、先用一句话说明要做什么

这不是简单地把 Figma 截图搬进网页，也不是单独写一个给 AI 看的 Skill。

目标是建立一套统一的设计知识底座：**人可以通过网页直观查找，AI 可以通过明确规则准确读取，设计和研发可以确认事实，管理员可以持续更新发布。**

最终应形成下面这条闭环：

```text
Figma、研发实现、现有文档
          ↓
经过整理和人工确认的权威档案
          ↓
    ┌─────┴─────┐
    ↓           ↓
团队查询网页    AI 查询与生成
    ↓           ↓
使用反馈、错误发现、设计更新
          ↓
      再次审核发布
```

## 二、为什么现在不能只继续完善网页

当前卡片查找器已经完成了一轮大范围扫描，形成了可继续利用的原始材料：

- 97 个卡片编号。
- 419 个设计页面 Frame。
- 422 条“页面—卡片”候选关系。
- 93 张本地卡片预览图。
- 419 张页面预览图。

这些成果适合作为“证据层”，但还不能直接作为最终规范，主要原因是：

1. Figma 节点名称只能证明设计稿里出现过某个命名，不能自动证明业务含义完全正确。
2. 相似 Frame 可能只是视觉接近，并不一定属于同一卡片编号。
3. 同一编号可能存在端型、状态、历史版本或实验变体。
4. Figma 通常不会完整记录使用目的、字段约束、废弃关系和测试规则。
5. 当前的 `confirmed` 更接近“Figma 可追溯”，不等同于已经经过设计或研发确认。

因此，下一步的重点应从“扫描更多”转为“建立语义、证据和确认机制”。

## 三、理想知识库最终包含什么

### 3.1 给产品、研发、测试使用的查询网页

这是团队日常真正打开使用的入口，应提供：

- 输入编号、名称或业务关键词查找组件。
- 通过缩略图和分类可视化浏览，不必只依赖文字搜索。
- 从一张卡片查看它使用在哪些设计页面。
- 从一个页面反查当前页面使用了哪些卡片。
- 查看卡片的标准预览、用途、内容结构、状态和变体。
- 并排比较容易混淆的卡片。
- 查看 Figma 原始位置和研发映射。
- 清楚区分“已人工确认”“Figma 可追溯”“待复核”。
- 按角色切换重点信息：产品看选型，研发看编号和字段，测试看状态和边界。

### 3.2 给管理员使用的整理与审核材料

第一期只有一位管理员统一整理和发布，因此不必马上建设复杂后台或数据库。管理员需要的是：

- 卡片总台账。
- 页面总台账。
- 页面与卡片关系表。
- 待确认清单。
- 缺图、缺说明、缺负责人和链接失效清单。
- 每次发布前的检查报告。
- 本次新增、修改、废弃内容的版本说明。

### 3.3 给 AI 使用的知识说明和查询入口

AI 需要的不是一份无限长的 Markdown，而是：

- 一份简短的总说明：告诉 AI 去哪里查、按什么顺序查。
- 一套经过确认的结构化档案：类似字段统一的电子总表。
- 按组件、页面和规则拆分的说明文档。
- 与文字对应的标准预览图和页面证据图。
- 明确的判断边界：哪些可以直接回答，哪些只能说明“待确认”。
- 稳定的查询方式：按编号、页面、分类、状态和版本获得准确结果。

### 3.4 最终交付物清单

| 交付物 | 面向对象 | 作用 |
| --- | --- | --- |
| 设计规范查询网站 | 全团队 | 搜索、浏览、反查、对比 |
| 卡片与组件权威档案 | 管理员、设计、研发、AI | 保存经过确认的事实 |
| 页面档案与使用关系 | 产品、设计、研发、测试 | 形成双向追溯 |
| AI 操作说明 | AI、工具维护者 | 约束查询顺序和回答方式 |
| 视觉素材库 | 人和 AI | 提供标准预览与证据 |
| 审核与质量报告 | 管理员、负责人 | 发布前发现问题 |
| 版本记录 | 全团队 | 了解新增、修改、废弃和替代 |

## 四、建设时必须坚持的九条原则

### 原则 1：只有一个权威来源

卡片名称、状态、用途和关系不能在网页、Markdown、Excel 中分别人工维护。应维护一份统一总台账，网页和 AI 文档从它生成，避免多份资料互相矛盾。

### 原则 2：视觉和文字必须同时存在

只有文字，用户难以找卡；只有截图，AI 无法理解业务含义。每条规范都应同时具备预览图、结构化字段和语义说明。

### 原则 3：证据和结论分开

“节点叫 card/20040”是证据；“这个页面确认使用 20040”是结论。系统必须保留证据来源，并记录结论是否经过人工审核。

### 原则 4：AI 不得补猜缺失事实

没有负责人确认的用途、字段、替代关系和状态，AI 应明确回答“资料未确认”，不能根据视觉自行补齐。

### 原则 5：从少量高质量样板开始

先把一个卡片家族做透，再复制模板。不要一开始同时整理全部卡片、颜色、按钮、导航和页面模式。

### 原则 6：按需展开，不做一个巨型文档

总说明只负责导航；卡片、页面、基础规范和组合模式分别存放。使用者和 AI 需要什么就读取什么。

### 原则 7：同时服务不同角色

同一份事实底座可以共用，但产品、设计、研发、测试看到的信息重点不同。

### 原则 8：任何内容都有状态和版本

至少区分使用中、试验中、拟废弃、已废弃、已替代，并记录最后确认时间。

### 原则 9：可检查比“看起来完整”更重要

发布前应能自动发现缺图、重复编号、无效链接、矛盾关系和长期未确认内容。

## 五、知识库应该覆盖哪些设计内容

知识库可以逐步扩展为六层，不应只停留在卡片。

### 第一层：设计理念与总原则

- 值得买的品牌体验目标。
- 内容与消费决策场景中的设计原则。
- 信息可信、价格透明、社区感和效率等体验原则。
- 设计决策时的优先级和取舍方法。

这一层回答：“为什么这样设计？”

### 第二层：基础视觉规范

- 品牌色、功能色和内容色。
- 字体、字号、字重和行高。
- 间距、栅格、圆角和阴影。
- 图标风格与尺寸。
- 图片比例、裁切和占位规则。
- 深色模式、无障碍和多端适配。

这一层回答：“界面的基础视觉语言是什么？”

### 第三层：组件规范

- 卡片。
- 按钮、标签、价格、优惠信息。
- 导航、Tab、筛选器、搜索框。
- 弹窗、浮层、Toast、加载和空状态。
- 评论、收藏、分享等内容社区组件。

这一层回答：“有哪些可复用零件，应该怎么用？”

### 第四层：页面和组合模式

- 首页推荐流。
- 搜索结果页。
- 好价列表和商品详情。
- 内容详情、评论区和个人主页。
- 表单、筛选、列表、详情等通用结构。

这一层回答：“组件如何组合成完整页面？”

### 第五层：交互、内容和状态规范

- 点击、展开、刷新、分页、返回等交互。
- 加载中、无数据、失败、失效、下架等状态。
- 标题、价格、标签、按钮文案等内容规则。
- 动效、反馈和异常恢复。

这一层回答：“页面在不同情况下如何变化？”

### 第六层：研发与测试映射

- 设计编号对应哪个研发组件或接口字段。
- 必填、选填和条件展示字段。
- 支持的平台和版本。
- 测试场景、边界条件和验收标准。

这一层回答：“如何准确实现和验证？”

## 六、每类档案具体要记录什么

### 6.1 一张卡片或一个组件的标准档案

| 信息 | 说明 |
| --- | --- |
| 编号 | 唯一编号，例如 20040 |
| 标准名称 | 团队统一使用的名称 |
| 所属家族 | 首页双列、好价列表等 |
| 标准预览 | 默认状态的清晰图片 |
| 使用目的 | 它解决什么问题 |
| 适用场景 | 什么时候使用 |
| 不适用场景 | 什么时候不要使用 |
| 内容结构 | 标题、图片、价格、标签等区域 |
| 必填与选填 | 哪些内容必须出现 |
| 状态和变体 | 默认、加载、失效、补贴等 |
| 相似组件 | 容易混淆的编号 |
| 主要差异 | 与相似组件的关键区别 |
| 使用页面 | 经过确认或待复核的页面 |
| 设计来源 | Figma 页面和节点链接 |
| 研发映射 | 组件名、接口编号或字段 |
| 生命周期 | 使用中、试验、废弃、被替代 |
| 负责人 | 可确认内容的人 |
| 确认状态 | 已确认、可追溯、待复核 |
| 最后更新时间 | 判断资料是否仍然新鲜 |

### 6.2 一个页面的标准档案

- 页面名称、业务模块和端型。
- 页面缩略图和完整预览。
- Figma 原始链接与版本。
- 页面包含的卡片和组件编号。
- 每条使用关系的证据。
- 页面状态：设计中、已上线、历史版本、已废弃。
- 负责人和最后确认时间。

### 6.3 一条“页面—卡片”关系的标准档案

- 页面是谁。
- 卡片是谁。
- 证据来自组件实例、规范命名、研发编号还是视觉复核。
- 证据节点与截图。
- 当前确认等级。
- 确认人、确认时间和备注。

关系必须只维护一次，系统自动同时展示在“卡片详情”和“页面详情”中，避免双向手工填写产生不一致。

### 6.4 一条基础规范的标准档案

以颜色或间距为例，应记录：

- 规范名称与用途。
- 标准值和允许范围。
- 正确示例与错误示例。
- 适用组件和页面。
- 研发变量名称。
- 可访问性要求。
- 版本和变更记录。

## 七、证据与确认等级

建议统一使用以下四级状态：

| 状态 | 含义 | 是否可作为最终事实 |
| --- | --- | --- |
| 已人工确认 | 设计或研发确认，且有确认记录 | 是 |
| Figma 可追溯 | 能追溯到组件实例或明确规范命名 | 可作为强证据，但应标明来源 |
| 推测匹配 | 根据编号、命名、尺寸或视觉相似推测 | 否，必须进入待确认清单 |
| 未知 | 缺少足够信息 | 否 |

当前数据中的 `confirmed` 建议统一调整为“Figma 可追溯”；只有设计或研发确认后，才升级为“已人工确认”。

## 八、完整建设路径

### 阶段 0：确定项目边界和规则

先回答并形成一页书面约定：

- 第一批覆盖哪些端和业务范围。
- 谁能确认组件档案。
- 谁能确认页面使用关系。
- 什么叫“完整”。
- 什么叫“已确认”。
- 废弃内容是否保留以及如何展示。
- 管理员多久发布一次。

阶段产出：项目章程、术语表、确认状态说明、负责人名单。

### 阶段 1：选择一个卡片家族做高质量样板

建议从 `20xxx 首页双列` 中选择 10～15 张代表性卡片，覆盖：

- 最常用卡片。
- 容易混淆的卡片。
- 有多个状态的卡片。
- 能在设计页面中找到明确实例的卡片。
- 至少一张存在待确认问题的卡片。

具体步骤：

1. 从 Figma 选出每张卡片的标准节点。
2. 生成统一尺寸的预览图。
3. 填写用途、结构、状态和相似差异。
4. 整理页面使用证据。
5. 设计或研发逐条确认。
6. 制作卡片详情和页面详情样板。
7. 用真实问题测试产品、研发和测试是否找得到答案。

阶段产出：卡片档案模板、页面档案模板、关系模板、审核流程、网页样板。

### 阶段 2：扩展到全部卡片

样板确认后再批量处理：

1. 按家族逐组整理，而不是按 Figma 页面顺序整理。
2. 自动提取编号、节点、截图和候选页面关系。
3. 管理员补充或修正语义。
4. 设计和研发只集中审核存在歧义的部分。
5. 发布前运行完整性检查。

阶段产出：完整卡片档案、双向页面关系、待复核清单、正式查询网站。

### 阶段 3：扩展基础视觉和通用组件

建议优先顺序：

1. 颜色、字体、间距、圆角、图片比例。
2. 价格、标签、按钮、导航、Tab、筛选等高频组件。
3. 加载、空、失败、失效等通用状态。

每新增一类规范，都复用卡片阶段已经验证的档案、证据、审核和发布机制。

阶段产出：值得买基础视觉规范、通用组件库、正确与错误示例。

### 阶段 4：建设页面模式和业务模式

将高频页面从“截图集合”提升为“可解释的组合模式”，说明：

- 页面目标。
- 信息优先级。
- 推荐结构。
- 可替换组件。
- 状态变化。
- 适用和不适用场景。

阶段产出：首页、搜索、好价、详情、内容和社区等页面模式库。

### 阶段 5：接入 AI 查询和设计辅助

在知识底座稳定后再加入：

- 自然语言查询：“20040 用在哪些页面？”
- 选型辅助：“首页双列有补贴信息应该用哪个编号？”
- 对比解释：“20040 和 20041 有什么区别？”
- 页面检查：“这个页面是否使用了已废弃卡片？”
- 设计辅助：“按值得买规范生成一个好价列表方案。”
- 研发与测试辅助：输出字段要求、状态清单和测试点。

AI 返回答案时必须同时给出来源、版本和确认状态。

## 九、AI 操作说明应该怎么写

AI 操作说明保持简短，主要规定工作顺序：

1. 先识别用户要查的是基础规范、组件、页面还是使用关系。
2. 优先读取权威档案，不凭记忆回答编号和属性。
3. 涉及视觉判断时，同时查看标准预览图和文字说明。
4. 涉及页面关系时，必须返回证据和确认等级。
5. 相似卡片必须先比较差异，不能只根据外观选择。
6. 发现资料冲突时，报告冲突，不自行选择一个答案。
7. 未人工确认的内容必须明确标注。
8. 回答应根据角色调整：产品讲选型，研发讲字段，测试讲状态。
9. 生成新设计时只能使用“使用中”的规范，除非用户明确要求历史版本。
10. 每次回答注明使用的知识库版本。

AI 说明不是知识本身，而是“如何正确使用知识”的操作手册。

## 十、查询网页的理想功能

### 第一版必须具备

- 卡片缩略图网格。
- 编号和关键词搜索。
- 分类、状态和确认等级筛选。
- 卡片详情。
- 页面详情。
- 卡片到页面、页面到卡片的双向查询。
- Figma 原始链接。
- 待复核清单。
- 手机和电脑基本适配。

### 第二版可以增加

- 相似卡片并排对比。
- 产品、设计、研发、测试角色视图。
- 本次更新内容展示。
- 废弃和替代提醒。
- 分享指定卡片或页面的直达链接。

### 后续智能能力

- 自然语言问答。
- 根据页面截图推荐可能的卡片编号。
- 自动发现设计稿中疑似使用旧卡片的页面。
- 自动生成组件使用报告和测试清单。

“上传截图自动识别卡片”具有较高误判风险，应在权威档案和相似卡片规则稳定后再做。

## 十一、管理员的日常维护流程

```text
收到新增或修改
      ↓
更新权威档案和预览图
      ↓
自动生成候选页面关系
      ↓
管理员整理待确认项
      ↓
设计或研发确认
      ↓
运行发布前检查
      ↓
重新生成并发布网页
      ↓
记录版本说明
```

第一期保持单管理员发布，静态网页即可满足。只有出现以下情况时再考虑数据库和正式后台：

- 多位人员需要同时编辑。
- 需要在线审批和权限控制。
- 需要实时同步 Figma 或研发系统。
- 需要保留完整操作日志。
- 发布频率明显提高，手工发布成为负担。

## 十二、团队分工建议

| 角色 | 主要责任 |
| --- | --- |
| 设计系统负责人 | 定义分类、命名、视觉和使用规则 |
| 业务设计 | 确认页面使用关系、补充真实场景 |
| 研发代表 | 确认编号、实现组件、接口字段和版本 |
| 测试代表 | 补充状态、边界条件和验收规则 |
| 管理员 | 整理档案、推进确认、检查和发布 |
| AI/工具维护者 | 维护查询规则、自动生成和质量检查 |

重要原则：AI 和脚本负责提取与提示，人负责业务语义和最终确认。

## 十三、发布前质量标准

### 13.1 单条组件档案合格条件

- 编号唯一。
- 有标准名称和分类。
- 有至少一张清晰预览图。
- 有用途和适用场景。
- 有状态和相似组件说明。
- Figma 来源可打开。
- 有负责人和最后更新时间。
- 确认等级明确。

### 13.2 一条页面关系合格条件

- 页面和组件均存在。
- 证据节点或截图存在。
- 证据来源明确。
- 确认状态明确。
- 人工确认时记录确认人和时间。

### 13.3 试点阶段建议目标

- 试点卡片档案完整率 100%。
- 试点卡片标准预览覆盖率 100%。
- 试点页面关系人工确认率 100%。
- 预设查询问题回答正确率达到 90% 以上。
- 不允许把待复核关系展示成已确认事实。

### 13.4 全量阶段持续观察指标

- 活跃组件档案完整率。
- 标准预览覆盖率。
- 人工确认关系占比。
- 超过约定期限未更新的档案数量。
- 无效 Figma 链接数量。
- 重复或冲突编号数量。
- 用户搜索后仍找不到结果的关键词。
- AI 回答中“无依据推断”的问题数量。

## 十四、用真实问题验收，而不是只看页面是否漂亮

试点至少用以下问题进行测试：

### 产品问题

- 首页双列展示补贴信息应该选哪张卡片？
- 20040 和相似卡片有什么区别？
- 哪些页面正在使用 20040？

### 设计问题

- 这张卡片有哪些正式变体？
- 页面里的这个 Frame 是标准组件还是手工绘制？
- 哪些页面仍然使用旧版卡片？

### 研发问题

- 20040 对应哪个组件或接口编号？
- 必填字段和可选字段有哪些？
- 空值、长标题和失效状态如何表现？

### 测试问题

- 这张卡片需要覆盖哪些状态？
- 哪些页面需要回归测试？
- 当前设计和研发映射是否已经确认？

如果这些问题无法稳定回答，即使网页视觉效果很好，也不能认为知识库已经完成。

## 十五、从 Ant Design 可以直接学习什么

### 15.1 把人类文档转成 AI 可直接读取的文档

Ant Design 提供了：

- `llms.txt`：AI 文档导航。
- `llms-full.txt` / `llms-full-cn.txt`：完整中英文组件文档。
- 单组件 Markdown 地址。
- 组件语义结构 Markdown。
- `design.md`：面向 AI 设计工具的整体设计语言说明。

值得买可以对应建设：

- 设计规范总导航。
- 完整规范汇总文件。
- 单组件、单卡片和单页面文档。
- 组件内部区域与用途说明。
- 值得买整体设计语言文档。

参考：[Ant Design LLMs.txt 说明](https://ant.design/docs/react/llms/)

### 15.2 不让 AI 靠记忆，提供准确查询工具

Ant Design CLI 可以查询组件列表、属性、完整文档、示例、设计变量、语义结构和版本变化，并输出便于 AI 使用的结构化结果。

值得买可以对应建设：

- 按编号查组件。
- 按组件查页面。
- 按页面反查组件。
- 对比两个组件。
- 查询基础设计变量。
- 查询版本变化。
- 检查缺图、冲突、废弃使用和未确认关系。

参考：[Ant Design CLI](https://github.com/ant-design/ant-design-cli)

### 15.3 Skill 负责决策流程，而不是堆积全部资料

`antd-skill` 的上层 Skill 重点规定范围、查询顺序、技术决策和检查要求；Ant Design X Skills 则按组件、SDK、Markdown、Card 等任务拆分专项说明。

值得买可以对应建设：

- 一个总 Skill：识别用户问题并路由到正确资料。
- 卡片专项说明。
- 基础视觉专项说明。
- 页面模式专项说明。
- 研发还原与测试专项说明。

参考：

- [Ant Design Skills 仓库](https://github.com/ant-design/antd-skill)
- [Ant Design 上层决策 Skill](https://github.com/ant-design/antd-skill/blob/main/skills/ant-design/SKILL.md)
- [Ant Design X Skills 介绍](https://x.ant.design/x-skills/introduce-cn/)
- [X Components Skill](https://github.com/ant-design/x/blob/main/packages/x-skill/skills-zh/x-components/SKILL.md)
- [X Card Skill](https://github.com/ant-design/x/blob/main/packages/x-skill/skills-zh/x-card/SKILL.md)

### 15.4 设计规范不仅是组件清单，还包括价值、原则和页面模式

Ant Design 从设计价值出发，再延伸到视觉语言、组件和列表页、详情页、数据可视化页等页面模式。它强调通过抽象和模块化降低协作成本。

值得买也不应只记录“有哪些卡片”，还要逐步说明：为什么使用、如何组合、在什么业务目标下选择。

参考：

- [Ant Design 设计体系介绍](https://ant.design/docs/spec/introduce/)

- [Ant Design 布局规范](https://ant.design/docs/spec/layout/)
- [Ant Design 列表页模式](https://ant.design/docs/spec/research-list/)
- [Ant Design 详情页模式](https://ant.design/docs/spec/detail-page/)
- [Ant Design 数据可视化页面模式](https://ant.design/docs/spec/visualization-page/)

### 15.5 把视觉变量、组件结构和版本变化分开管理

Ant Design 将整体设计语言、设计变量、单组件属性、语义结构和版本变更分别提供查询入口。这能减少 AI 混淆，也方便按问题读取最小必要信息。

值得买应对应区分：

- 设计原则。
- 基础视觉变量。
- 组件档案。
- 组件内部结构。
- 页面组合模式。
- 版本和变更记录。

参考：[Ant Design 主题与 Design Token](https://ant.design/docs/react/customize-theme/)

| lint / doctor | 缺图、冲突、废弃使用和链接检查 |

## 十七、主要风险和应对方式

| 风险 | 表现 | 应对方式 |
| --- | --- | --- |
| 一次覆盖太多 | 数量很大但语义粗糙 | 先做一个家族样板 |
| Figma 被当作唯一真相 | 缺少业务和研发信息 | 设计、研发共同确认 |
| 多份资料冲突 | 网页、表格、MD 不一致 | 只维护一份权威总台账 |
| AI 根据截图猜编号 | 相似卡片误判 | 要求证据和确认等级 |
| 文档快速过期 | 新版本上线但资料未更新 | 负责人、版本和更新时间必填 |
| 管理成本过高 | 每次更新都大量手工操作 | 自动提取、自动生成、集中审核 |
| 只服务设计 | 产品、研发、测试仍然难用 | 按角色设计详情视图 |
| 过早建设复杂后台 | 开发成本高、规则仍未稳定 | 第一期使用静态网页和单管理员发布 |

## 十八、建议的近期行动

### 第一步：确定试点清单

从 `20xxx 首页双列` 中选出 10～15 张代表卡片，并列出对应的真实设计页面。

### 第二步：确认档案字段

由产品、设计、研发、测试各看一遍本文件“第六章”，删除无价值字段，补充遗漏字段。

### 第三步：完成一张示范档案

建议先用 `20040` 制作完整样板，包括标准预览、用途、结构、变体、相似差异、页面关系和确认记录。

### 第四步：进行一次小范围评审

让一位设计和一位研发确认示范档案，再邀请产品和测试分别完成三项查询任务。

### 第五步：锁定模板并批量整理

模板没有通过前不要全量铺开；模板通过后再按家族批量处理。

## 十九、第一阶段完成的判断标准

当以下事项都满足时，才算卡片知识库第一阶段完成：

- 团队可以通过图片和关键词找到目标卡片。
- 任意试点卡片都能查看用途、状态、相似差异和来源。
- 任意试点卡片都能反查使用页面。
- 任意试点页面都能反查使用卡片。
- 每条关系都能看到证据和确认等级。
- 产品、研发和测试能分别得到自己需要的信息。
- AI 能回答预设问题，并明确区分事实与待确认内容。
- 管理员能够在不修改网页代码的情况下更新资料并重新发布。

## 二十、结论

理想的“设计规范 AI 知识库”不是一个文件、一个网站或一个 Skill，而是一套持续运转的体系：

> **权威档案负责事实，图片负责视觉，网页负责查找，Skill 负责约束 AI，审核流程负责可信，版本机制负责长期有效。**

值得买当前最合适的路径，是先以卡片库作为第一个完整模块，建立模板、证据、确认和发布闭环；验证成功后，再逐步扩展到基础视觉、通用组件、交互状态和页面模式，最终形成能够同时服务产品、设计、研发、测试与 AI 的完整设计知识底座。
