# 卡片知识库治理与确认规则

版本：`2026.09.01-r1`

## 已确定的业务规则

1. 一个编号代表一种卡片类型。
2. 同一编号可以有多个状态变体，所有状态归档在该编号之下，不拆成新卡片。
3. 除明确废弃或置灰的卡片外，其他卡片默认按“使用中”保留。
4. 实验、历史、AB 分流等复杂业务字段先保留为空，不自动推测；后续随业务迭代补全。
5. 设计编号与研发编号永远一一对应。
6. 不同端默认共用编号和规范；发现例外时进入待确认清单。
7. 长时间无人确认的内容默认保留，不删除、不自动废弃。
8. 卡片的新增、废弃、状态变更和页面关系，均应保留来源、确认人和版本记录。

## 谁负责确认

- 设计部门成员可以确认卡片的设计编号、视觉样式、状态变体、用途和设计页面使用关系。
- 负责该模块的研发可以确认研发组件、接口编号、字段限制和线上实际实现。
- 产品负责确认会改变业务含义、用户行为或分流逻辑的争议。

## 设计和研发不一致时怎么办

设计和研发不一致不能简单选择一方覆盖另一方，应同时记录两个事实：

- “规范应当是什么”由设计确认。
- “线上当前实现是什么”由负责研发确认。

如果差异仅影响视觉还原，由设计系统负责人给出规范结论，研发记录修复计划或保留原因；如果差异影响业务逻辑、字段或用户行为，由产品、设计、研发共同确认最终结论。

第一期只覆盖设计稿，因此卡片档案以设计确认结果为准；发现研发差异时标记为“实现待对齐”，不修改设计事实。

## 关系的证据等级

| 等级 | 含义 | 是否已经人工确认 |
| --- | --- | --- |
| 已人工确认 | 设计或研发明确确认并记录 | 是 |
| Figma 可追溯 | 页面中存在卡片组件实例或明确完整节点 | 否，是强证据 |
| 推测匹配 | 普通 Frame、资源命名或视觉相似 | 否，需复核 |
| 未知 | 缺少足够信息 | 否 |

原始数据中的 `confirmed` 只表示“Figma 可追溯”，不再对外显示为“已确认”。

## 保留和删除规则

- 未确认不等于无效。
- 长期无人确认继续保留，并显示最后更新时间。
- 只有明确收到废弃结论时才能标记为废弃。
- 已废弃内容仍保留历史档案、替代编号和使用证据，不直接删除。
- 错误识别的页面关系可以驳回，但要保留驳回原因和审核记录。

## 版本建议

知识库版本与 App 产品版本分开管理，采用容易理解的日期版本：

```text
2026.09.01-r1
```

- `2026.09.01`：本次正式发布日期。
- `r1`：同一天的第 1 次发布；如果当天修正后重发，则为 `r2`。

每张卡片同时记录：

- 首次进入知识库的版本。
- 最后修改版本。
- 明确废弃版本（没有则为空）。
- 对应 App 版本（第一期可以为空，后续需要时补充）。

## 推荐的确认通知方式

第一阶段采用：

1. 管理员生成“本次新增、变更、待确认”网页清单。
2. 飞书 Bot 在设计群发送摘要和清单链接。
3. 设计师打开网页查看卡片图片、状态和 Figma 证据。
4. 确认结果由管理员统一合并发布。

这种方式不要求每位设计师安装 Figma 插件，适合先验证流程。

后续如果新增和废弃频率较高，再开发 Figma 插件，在卡片库内提供“提交新增”“提交变体”“申请废弃”入口。插件只负责提交，不直接自动发布，最终仍经过确认流程。
