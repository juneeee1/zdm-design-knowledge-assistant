# 值得买设计知识助手 · MVP 产品与实施方案

日期：2026-09-14。状态：实施建议，尚未开始本方案中的产品开发或远程发布。

## 1. 产品目标

让设计、产品、研发通过自然语言找到现有设计依据，比较候选卡片，并生成带来源的评审材料。提供网页直接体验和 AI 工具安装两种入口，使用同一份有版本的知识。

首期完整覆盖已收录资料的查阅能力；推荐、评审和生成能力按证据成熟度提供。资料全量接入不等于每条业务语义已经补齐。

## 2. 已有基础与差距

已有 261 条卡片记录、419 个原始 Frame、486 条页面关系、26 篇精炼档案和 12 张重点卡片评审样板。卡片快照版本为 2026.09.01-r2；当前精炼知识版本为 2026.09.11-r1。393 条关系可追溯到 Figma，人工确认关系为 0。

已有静态查询页面、查询脚本、卡片 Skill、来源和待确认事项、构建和完整性校验。当前不是在线 AI 聊天产品，也不是已经发布的一键安装器。根 package.json 没有安装器 bin 入口，仍为 private。

本轮只读检查：GitHub CLI 已登录 juneeee1；本项目尚无 Git 远程。公司 GitLab 首页返回登录跳转，未核验项目创建权限、Package Registry、CI Runner、Pages 或后端托管。DaMo 文件目录接口仅返回封面和 Logo，不能以此断定全文件只有两页；已有介绍页记录证明需要继续检查读取范围。卡片链接仍指向封面。Figma 团队目录链接是查找文件的入口，不等于已取得团队全量内容。

## 3. 两个用户入口

### 网页入口：用于演示与团队日常查询

打开网址即可看到可用的提问区和知识浏览。首屏提供“找卡片”“比差异”“做评审”三个任务入口；展示知识版本与更新时间。

标准路径：输入问题 → 查询真实资料 → 展示结论和候选 → 展开来源/预览 → 继续追问 → 保存或导出评审稿。

桌面布局建议：左侧历史任务，中间问答与结果，右侧按需展开来源与预览。避免三栏同时堆满；窄屏采用抽屉或独立详情页。卡片对比使用专用并列视图，长备注按需展开。

访客可先用内置案例提问，也能自由输入。案例仍经过真实检索和模型回答，不以预置答案伪装 AI。演示站由服务端配置模型，访客无需填写密钥。缺少模型服务时明确提供“知识检索模式”，不伪装生成能力。

### 安装入口：用于已有 AI 工具的工作流

安装程序检查 Node 环境，让用户选择检测到的工具或手动指定工具，安装统一 Skill、查询脚本、知识快照与图片，再进行健康检查。先验证 Codex，随后适配 Cursor、Claude Code。

建议默认安装在当前项目范围，明确显示目标位置；全局安装作为显式选项。已有安装检测版本，升级前保留回退副本。卸载只删除安装清单记录的文件，保留用户改动。

发布后提供一条实际测试过的固定版本命令，以及 install、update、doctor、uninstall。仓库名和命令在创建仓库、验证包入口后定稿；此前所有 npx 命令仅为体验示意。

Skill 使用宿主 AI 工具已有的模型能力，查询本地知识。不会在任意工具中保证同样的图片排版或自动触发效果；图片不支持内嵌时提供预览路径和网页入口。网页中的 X Card 不会自动嵌入 Codex 等宿主工具。

## 4. 首期功能范围

| 功能 | 用户输入 | 实际交付 | 边界 |
| --- | --- | --- | --- |
| 查编号与规则 | 编号、名称、自然语言 | 标准预览、规则摘要、来源、版本 | 不混淆当前知识版本与原始扫描版本 |
| 找候选卡片 | 页面、目标端、内容类型 | 2～5 个候选、匹配依据、缺少条件 | 未确认的用途只作为候选，不强推唯一答案 |
| 比较卡片 | 两个编号或候选选择 | 原始差异、配置、状态和疑问 | 没有正式差异时明确说明 |
| 查页面关系 | 页面或编号 | 按业务分类组织的 Frame 证据 | 分开可追溯、推断、人工确认和被拒绝关系 |
| 准备评审 | 简短需求描述 | 设计说明、字段草案、测试建议 | 草案不是已实现的接口或已批准规范 |
| 反馈纠错 | 指定答案或档案 | 保存问题、关联来源与知识版本 | 不自动修改正式规则 |
| 历史与导出 | 当前会话 | 本浏览器历史、Markdown、打印视图 | 首期不承诺多设备账号同步 |
| 安装与升级 | 单条命令 | 项目级 Skill、知识包、健康报告 | 新设备需有 Node 和可用的宿主 AI 工具 |

Figma 页面自动审查作为后续增强：先限定一个已授权的页面及可验证规则，再增加节点与实例检查。现有数据不足以首期承诺全站像素还原、任意截图识别编号、完整代码生成和自动发布上线。

## 5. 一次回答如何产生

1. 识别任务：查编号、查规则、找候选、比较或准备评审。只有会改变结果的缺失信息才追问，例如 PC/App。
2. 调用查询工具：编号精确匹配优先；主题和备注检索补充候选；页面关系由结构化数据读取。
3. 构建证据：每条证据保留编号、节点、端型、版本和确认状态。历史备注不自动覆盖现行结论。
4. 模型组织答案：只能引用检索到的证据；建议和来源事实分开，缺证据不补造。
5. 服务端检查输出：引用 ID 必须存在；卡片、图片和 Figma 链接由系统根据 ID 生成，不能由模型任意拼写。
6. 前端展示固定结果类型：候选列表、双卡对比、来源条目、待确认事项、评审文档。
7. 保存本次问题、答案和证据版本，追问保留上下文。知识升级后历史记录标明旧版本，不静默改写历史答案。

首期采用精确编号、关键词、业务别名和关系查询。自然语言交给模型转成受约束的查询条件；先评估检索失败案例，再决定是否增加向量检索。

## 6. Figma 资料如何补齐

两份指定文件优先。先核对文件与页面目录完整性，记录能读和未读范围，再读取关键节点。团队目录用于定位已知资料缺口，文件范围确认后再扩展。

DaMo 首批整理颜色、文字、间距、圆角等可读到的变量/样式及按钮、标签、价格、导航、浮层等高频组件。它们是采集目标，不能预先宣称已经取得。记录变量集合、模式、别名、组件属性、默认值、状态、说明及标准预览。

卡片库继续使用现有编号工具和源项目同步链路。每张卡片记录本体与旁注边界；完整原始信息可查询，重点样板补业务解释。版本冲突和未命名变体进入问题队列。

Figma 采集不放在每次提问的关键路径。构建稳定快照供查询，提供来源跳转；更新时人工触发同步、查看差异并发布新版本。预览保存为本地版本资产，不依赖短期有效的导出链接。

## 7. Ant Design X 的采用方式

采用 React + Ant Design / Ant Design X 构建对话界面和结果组件；保留现有 Markdown、JSON、查询逻辑和校验规则。

X SDK 用于消息、会话状态、流式请求及取消/重试。它不是模型服务，也不是知识检索系统。

X Card 可承载受限制的结果模板；首期只注册候选卡、对比、来源和问题等确定的组件。真实交互调用经过校验的服务端操作。不要求 AI 任意生成整页结构。

Skill 封装值得买自己的查询流程、证据约束和输出契约；Ant 的开发 Skill 可以辅助实现其组件，但不作为值得买业务规范来源。

## 8. 服务与数据

网页端需要一个 Node 服务，负责查询、调用模型、校验引用与处理反馈。部署采用可运行 Node 的容器或服务平台；静态页面托管只能承担前端。

本地先验证一个 OpenAI-compatible 模型接口。使用服务端环境变量保存地址、模型名和密钥，不放入浏览器或知识包。需要实际的模型服务配置，GitHub/GitLab 登录和宿主工具订阅不能自动替代它。

首期知识为版本化文件，保持现有权威数据结构；服务端反馈使用 SQLite（需持久磁盘），部署环境没有持久磁盘时改用托管数据库。访客历史保存在本浏览器，提供清空。多个用户的回答请求相互隔离。

产品状态包含加载、停止、超时、重试、无匹配、无模型服务和部分证据不足。停止回答要取消请求；模型失败时仍保留知识查询结果。公开演示设置请求频率、并发和用量上限，并提供停止新访问的开关。

## 9. GitLab 优先的发布路线

第一步核实公司 GitLab 的实际项目空间、权限及 Package Registry。具备条件时，公司 GitLab 保存源代码、版本和知识包，发布固定版本安装包；CI 可用时自动执行检查和打包。

网页部署单独核实。GitLab Pages 适合静态前端，不能直接承担动态 Node 模型接口。需要公司可用服务部署能力，或将前后端部署到另一个支持 Node 的环境。

GitLab 条件不足时，可使用已登录的 GitHub 账号 juneeee1 建立完整体验仓库并分发安装包。GitHub 代码托管本身不等于在线 AI 应用托管。

按本次用户意图，体验版使用完整现有知识资料，不缩减为少量示例。平台登录、凭据及无关本地文件不属于发布内容。对外体验覆盖全量已收录资料，但不宣称公司全部 Figma 已采集。

临时公开结束需要分别处理仓库可见性、安装包下载、演示站和模型接口；仅改仓库私有不会必然关闭其他部署。已经安装的本地知识包可继续离线使用，不能承诺远程撤回。用户尚未指定确定关闭时间，本方案不创建自动关闭任务。

官方 GitLab Pages 说明：https://docs.gitlab.com/user/project/pages/

## 10. 分阶段交付与验收

| 阶段 | 交付 | 完成依据 |
| --- | --- | --- |
| A：资料与接口 | 采集范围清单、稳定快照、统一查询工具 | 编号/来源不丢失；未知值保留；现有查询测试继续通过 |
| B：真实问答 | 模型接入、检索、引用、追问、错误恢复 | 自由问题经过实际查询；无模型时状态明确 |
| C：产品界面 | 卡片预览、对比、历史、来源、反馈、导出 | 桌面/窄屏实测；结果和来源对应；刷新后历史保留 |
| D：安装与发布 | 固定版本安装器、doctor/update/uninstall、远程体验入口 | 干净目录完成安装、查询、升级和卸载；不覆盖用户文件 |
| E：试点 | 真实需求任务集和反馈整理 | 记录正确性、查找耗时和未解决问题，决定下一轮范围 |

不以写完界面作为结束。先建立约 20 个验收问题，覆盖精确编号、自然语言同义表达、两个编号比较、页面关系、未知差异、历史版本、无结果及失败恢复。标准答案指向已有来源，不给待确认问题编答案。

关键验收：引用可定位；同次回答与导出使用同版本；模型不虚构编号、代码字段或确认状态；重试不丢输入；浏览器实际测试图片、布局与交互。之前本地 HTML 的浏览器访问受阻，不代表已完成新 MVP 视觉验收，新产品需按允许的测试方式完成。

安装测试先承诺一个实际验证的宿主工具，其他适配完成后再列为支持。安装成功不等于宿主立即发现 Skill，按宿主实际机制提示刷新/重新打开任务并验证触发。

## 11. 领导演示脚本

先打开网页，问“帮我找首页展示原创笔记的卡片”，查看候选、预览和来源；再问“20040 和 20041 有什么区别”，展示原始差异与未确认分流；最后根据选定材料生成评审稿并导出。

随后在新项目执行已发布的安装命令，用宿主 AI 工具提出同样的问题，展示同一知识版本和相同事实依据。两入口的语言措辞可以不同，编号、来源、确认状态必须一致。

展示价值：从重复找资料和解释规则，推进到可追溯的查询、比较和评审交付。实际节省时间和减少返工的幅度由试点衡量。

## 12. 实施前需要落实的三项资源

1. 一个真实模型接口的服务端配置，用于网页自由问答。
2. GitLab 的目标项目及包发布/部署条件，或使用 GitHub 的具体仓库与 Node 托管环境。
3. Figma 的可读取文件范围及新增组件资产入口；读取失败的内容继续使用已有快照并登记缺口。

产品代码、安装器和本地检索的开发可以先推进。在线模型、远程发布和全量 Figma 扫描分别按资源核验结果接入；本方案不声称这些条件已经齐备。
