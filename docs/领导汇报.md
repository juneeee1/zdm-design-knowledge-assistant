# 值得买设计规范 AI 知识库 · 初版汇报

版本：2026.09.11-r1。定位：团队试用版，未完成人工确认的内容均有明确标记。

## 一句话价值

把分散在 Figma、卡片库和业务页面里的设计经验，整理成“人能查、AI 能引用、结论能追溯、问题能交接”的组织资产，为设计复用和 AI 辅助交付建立共同依据。

## 为什么值得做

过去找一个卡片或解释一个状态，经常需要翻设计稿、询问熟悉业务的人，再重新向研发解释。随着 AI 参与设计与开发，如果输入只是图片和一句风格要求，它难以知道编号、版本、业务条件和例外。知识库把这些信息放在同一条证据链里，减少每个需求都重新收集上下文的成本。

## 本版交付

| 交付 | 解决的问题 | 当前可用程度 |
| --- | --- | --- |
| 六层知识档案 | 规则分散、难以复用 | 可用于查阅与方案评审，来源与建议分开 |
| 卡片索引与标准预览 | 编号难找、相似卡片难追溯 | 可检索、看原始备注、定位 Figma 与页面证据 |
| 重点卡片评审档案 | 只有图片，缺少选择边界 | 有针对性的使用边界与测试建议，待业务确认 |
| 本地查询页面与命令 | 非技术同学与 AI 入口不一致 | 使用同一批源文档构建，支持搜索和来源追溯 |
| 待确认清单 | 疑问只留在聊天里 | 有优先级、责任角色、影响范围及关闭条件 |
| 自动校验 | 更新后遗漏与版本失配 | 检查编号、文件、引用、确认信息和构建一致性 |

实际数量以 [本版验收数据](本版验收数据.md) 为准，由构建脚本计算。不要把可追溯关系数量当成人工确认数量，也不要把 Frame 数当成业务页面数。

## 对各团队的价值

| 对象 | 工作变化 | 可观察的收益 |
| --- | --- | --- |
| 设计 | 从重复找稿、解释，转为引用档案和处理例外 | 查找耗时、重复咨询次数 |
| 产品 | 看到组件能力与未知条件 | 需求评审中的语义返工 |
| 研发 | 获得编号、来源与待补字段契约 | 因设计理解不一致产生的返工 |
| 测试 | 提前看到状态与边界检查点 | 状态覆盖率、边界遗漏 |
| 新同学 | 按问题进入资料，而非依赖个人记忆 | 独立完成查询任务的成功率 |
| AI | 在回答与生成前检索证据并说明不确定性 | 无依据结论率、来源引用准确率 |

本版尚未测量实际节省工时、转化率或交付周期，不能声称已达到任何提升百分比。以上是待验证的收益路径。

## 三分钟演示

1. 搜索“字号”，打开档案，展示数值对应的 Figma 节点、适用范围与待确认状态。
2. 搜索“20040”，查看原始卡片和精炼档案，再与 20041 对比。解释为什么系统保留差异问题而不编造选型答案。
3. 打开待确认清单，展示问卷未命名变体或视频比例冲突，说明这些问题如何交给负责人关闭。
4. 打开版本数据，展示可追溯与人工确认分开统计。强调知识库已经能支持协作，同时清楚显示成熟度。

## 下一步投入建议

先做一个真实需求的两周试点，建议由一名管理员协调，邀请设计、产品、研发、测试各一名代表参与；这是建议安排，并非已承诺排期。优先解决现行 DaMo 范围、关键卡片选型和代码映射三个 P0 问题。无需第一天就把所有档案逐条签字。

第一周选定需求与十个真实查询问题，记录旧方式基线，确认重点档案。第二周在同一难度任务上试用知识库，记录查找时间、正确性、引用来源与返工原因。评估通过后再扩展页面、组件和多人协作能力。

## 如何衡量，避免只看文档数量

| 指标 | 口径 | 采集方式 |
| --- | --- | --- |
| 查询成功率 | 独立找到正确答案且证据适用的任务数 / 全部任务数 | 由业务评审答案，保留失败原因 |
| 查询耗时 | 从提出问题到得到可用结论的中位耗时 | 同难度问题对照，避免熟悉题目偏差 |
| 来源准确率 | 引用确实支持结论的回答数 / 被抽检回答数 | 人工抽检节点、版本与端型 |
| 无依据结论率 | 把未知说成确定的回答数 / 被抽检回答数 | 未确认问题作为专门测试集 |
| 确认覆盖 | 已完成业务确认的试点档案 / 试点档案 | 不用全库扫描量充当分母 |
| 返工变化 | 因规则/状态误解产生的返工次数和耗时 | 按相近需求复杂度比较 |

## 当前边界与决策请求

DaMo 本轮覆盖介绍页而非全量组件与 Token；PC 仅获得公开文本，尚未完整视觉/交互实测；研发实现没有接入；新增规范与样板尚未人工批准。详见 [待确认清单](待确认清单.md)。

建议领导支持明确一个业务试点、一个维护责任人和每周短时评审窗口。近期目标是验证“能否更快得到可信答案”，再决定是否扩大投入建设在线服务、权限审批及设计到代码映射。
